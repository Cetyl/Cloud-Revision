# VisionTag

An AI image recognition platform on Amazon EKS. Upload a photo, get back ranked labels with confidence scores.

The application is deliberately simple. The point of this project is the platform underneath it: a production-shaped EKS environment with node autoscaling, pod-scoped IAM, observability, runtime security, cost controls, and a CI/CD pipeline.

## What this demonstrates

- A two-service application on Amazon EKS spread across two Availability Zones
- Calling Amazon Bedrock from pods with no static credentials, using IRSA
- Node autoscaling with Karpenter, including a hard cost ceiling
- Metrics, security findings, and per namespace spend on one dashboard
- Automated build and rolling deploy through CodePipeline, CodeBuild, and ECR

## Architecture

Traffic enters through Route 53 and an Application Load Balancer. The AWS Load Balancer Controller provisions that ALB from a standard Kubernetes Ingress resource, so the load balancer is described in the same manifests as the application.

Both workloads run as pods in private subnets. Nothing running application code is directly reachable from the internet, and outbound calls leave through NAT Gateways.

| Component | Stack | Role | Port |
| --- | --- | --- | --- |
| Frontend | React 18 + Vite, served by nginx | Landing page and classify UI, proxies `/api` to backend | 80 |
| Backend | FastAPI, Python 3.12 | Receives uploads, calls Bedrock, returns labels | 8000 |

Request path:

```
Browser
  → Route 53
  → Application Load Balancer  (public subnets, both AZs)
  → frontend pod  (nginx, private subnet)
  → visiontag-backend ClusterIP service
  → backend pod  (FastAPI, private subnet)
  → Amazon Bedrock  (egress via NAT Gateway, authenticated by IRSA)
```

The frontend's nginx does two jobs: SPA fallback so client-side routes such as `/classify` resolve to `index.html`, and reverse proxying `/api/` to the backend service so the browser only ever talks to one origin.

## Cost expectations, read before you start

Every resource below bills by the hour whether or not anyone uses the app. Approximate monthly figures for a small two-node setup running continuously in a US region, on-demand pricing:

| Resource | Approximate monthly |
| --- | --- |
| EKS control plane, $0.10/hr | ~$72 |
| 2 × t3.large worker nodes | ~$120 |
| 2 × NAT Gateway | ~$65 plus data processing |
| Application Load Balancer | ~$20 |
| ECR, S3, EBS | ~$10 |
| **Total, always on** | **~$285 to $300** |

Bedrock inference is a small fraction of that at learning volumes. The expensive items are NAT Gateways and idle nodes, not the model.

Two ways to cut this substantially:

- Tear the environment down between sessions. Running it only while you work brings the figure to roughly $30 to $50 per month.
- Use one NAT Gateway instead of two. You lose AZ redundancy for egress, which does not matter for a learning project.

Verify current pricing against the AWS pricing pages before relying on these numbers. **Create an AWS Budget with an email alert before you create the cluster.**

Local tooling:

```bash
aws --version        # AWS CLI v2
kubectl version --client
helm version

```

AWS setup:

```bash
aws configure         # set access key, secret, default region
aws sts get-caller-identity   # should return your account ID
```

You also need a vision-capable Bedrock model enabled. In the AWS Console go to **Bedrock → Model access**, enable the model you intend to use, and note its exact model ID.

Set these shell variables, they are used throughout:

```bash
export AWS_REGION=ap-south-1
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
export CLUSTER_NAME=visiontag-eks
export BEDROCK_MODEL_ID=anthropic.claude-3-5-sonnet-20240620-v1:0
```

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
export AWS_REGION=$AWS_REGION
export BEDROCK_MODEL_ID=$BEDROCK_MODEL_ID
uvicorn app.main:app --reload --port 8000
```

Verify the health endpoint:

```bash
curl http://localhost:8000/healthz
# {"status":"ok"}
```

Frontend, second terminal:

```bash
cd frontend
npm install
npm run dev
```

Open http://localhost:5173, click **Try It Now**, upload an image, click **Classify**.

**Success criteria:** you get back labels with confidence bars, a latency figure, and a pod name. If the Bedrock call fails, it is almost always the model ID or the region not matching where you enabled model access.

## Phase 1, network and cluster

### 1a. VPC

Console route: **VPC → Create VPC → VPC and more**. Settings:

- Number of Availability Zones: 2
- Public subnets: 2
- Private subnets: 2
- NAT gateways: 1 per AZ (or "In 1 AZ" to save cost)
- DNS hostnames and DNS resolution: enabled

Tag the private subnets and the cluster security group with `karpenter.sh/discovery = visiontag-eks`. Karpenter uses that tag in Phase 5 to find where to place nodes. Doing it now saves a return trip.

### 1b. Cluster

Console route: **EKS → Create cluster**.

- Name: `visiontag-eks`
- Kubernetes version: current default
- Cluster IAM role: create one if prompted
- Networking: select the VPC from 1a, choose the private subnets
- Cluster access: add your IAM user or role as an access entry with `AmazonEKSClusterAdminPolicy`, otherwise you will be locked out of kubectl

Creation takes 10 to 15 minutes.

Equivalent with eksctl, which also handles the VPC:

```bash
cat > cluster.yaml <<'EOF'
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: visiontag-eks
  region: ap-south-1
  version: "1.30"
iam:
  withOIDC: true
managedNodeGroups:
  - name: app-nodes
    instanceType: t3.large
    desiredCapacity: 2
    minSize: 2
    maxSize: 4
    privateNetworking: true
EOF

eksctl create cluster -f cluster.yaml
```

### 1c. Node group

If you used the console, add compute now: **your cluster → Compute → Add node group**. Instance type `t3.large`, desired 2, min 2, max 4, placed in the private subnets.

### 1d. Connect kubectl

```bash
aws eks update-kubeconfig --name $CLUSTER_NAME --region $AWS_REGION
kubectl get nodes
```

**Success criteria:** two nodes in `Ready` state.

### 1e. Confirm the OIDC provider

IRSA requires an OIDC provider associated with the cluster. eksctl with `withOIDC: true` does this for you. If you used the console:

```bash
aws eks describe-cluster --name $CLUSTER_NAME --region $AWS_REGION \
  --query "cluster.identity.oidc.issuer" --output text
```

If no IAM OIDC provider exists for that issuer yet:

```bash
eksctl utils associate-iam-oidc-provider \
  --cluster $CLUSTER_NAME --region $AWS_REGION --approve
```

## Phase 2, container images in ECR

Create the repositories:

```bash
aws ecr create-repository --repository-name visiontag-frontend --region $AWS_REGION
aws ecr create-repository --repository-name visiontag-backend  --region $AWS_REGION
```

Authenticate Docker:

```bash
aws ecr get-login-password --region $AWS_REGION \
  | docker login --username AWS --password-stdin $ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com
```

Build and push. Note `--platform linux/amd64`, which matters if you are on an Apple Silicon Mac and your nodes are x86:

```bash
export ECR_BASE=$ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com

docker build --platform linux/amd64 -t $ECR_BASE/visiontag-backend:v1 ./backend
docker push $ECR_BASE/visiontag-backend:v1

docker build --platform linux/amd64 -t $ECR_BASE/visiontag-frontend:v1 ./frontend
docker push $ECR_BASE/visiontag-frontend:v1
```

**Success criteria:** both repositories show a `v1` tag in the ECR console.

## Phase 3, IRSA for Bedrock

The goal is that backend pods can invoke exactly one Bedrock model and do nothing else, with no credentials stored anywhere.

### 3a. Create the permission policy

Edit `iam/bedrock-invoke-policy.json` so the region and model in the resource ARN match yours, then:

```bash
aws iam create-policy \
  --policy-name VisionTagBedrockInvoke \
  --policy-document file://iam/bedrock-invoke-policy.json
```

### 3b. Create the role with an OIDC trust relationship

The simple path, which creates the role, the trust policy, and the Kubernetes service account in one step:

```bash
kubectl apply -f k8s/namespace.yaml

eksctl create iamserviceaccount \
  --cluster $CLUSTER_NAME \
  --region $AWS_REGION \
  --namespace visiontag \
  --name bedrock-sa \
  --attach-policy-arn arn:aws:iam::$ACCOUNT_ID:policy/VisionTagBedrockInvoke \
  --approve
```

The manual path, if you prefer the console: use `iam/irsa-trust-policy.json` as the trust policy, substituting `<ACCOUNT_ID>`, `<REGION>`, and `<OIDC_ID>` (the last path segment of the OIDC issuer URL from Phase 1e). Attach `VisionTagBedrockInvoke` to that role, then put the role ARN into the annotation in `k8s/serviceaccount.yaml` and apply it:

```bash
kubectl apply -f k8s/serviceaccount.yaml
```

### 3c. Verify

```bash
kubectl get sa bedrock-sa -n visiontag -o yaml | grep role-arn
```

**Success criteria:** the service account carries an `eks.amazonaws.com/role-arn` annotation pointing at your role.

## Phase 4, load balancer controller and deploy

### 4a. Install the AWS Load Balancer Controller

Console route: **EKS → your cluster → Add-ons → Get more add-ons → AWS Load Balancer Controller**. The console can create the required IAM role for you.

Helm route:

```bash
curl -o iam-policy.json https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/main/docs/install/iam_policy.json

aws iam create-policy \
  --policy-name AWSLoadBalancerControllerIAMPolicy \
  --policy-document file://iam-policy.json

eksctl create iamserviceaccount \
  --cluster $CLUSTER_NAME --region $AWS_REGION \
  --namespace kube-system --name aws-load-balancer-controller \
  --attach-policy-arn arn:aws:iam::$ACCOUNT_ID:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve

helm repo add eks https://aws.github.io/eks-charts
helm repo update
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=$CLUSTER_NAME \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller
```

Confirm it is running:

```bash
kubectl get deployment -n kube-system aws-load-balancer-controller
```

### 4b. Point the manifests at your images

Replace the placeholder image URIs in both deployment manifests:

```bash
sed -i '' "s|<ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com|$ECR_BASE|g" \
  k8s/backend-deployment.yaml k8s/frontend-deployment.yaml
```

On Linux, drop the `''` after `-i`.

Also confirm `AWS_REGION` and `BEDROCK_MODEL_ID` in `k8s/backend-deployment.yaml` match your setup.

### 4c. Apply

```bash
kubectl apply -f k8s/backend-deployment.yaml -f k8s/backend-service.yaml
kubectl apply -f k8s/frontend-deployment.yaml -f k8s/frontend-service.yaml
kubectl apply -f k8s/ingress.yaml
```

Watch the rollout:

```bash
kubectl get pods -n visiontag -w
kubectl get ingress -n visiontag
```

The ALB takes two to three minutes to become active. When the `ADDRESS` column is populated, open it in a browser.

### 4d. Verify end to end

```bash
ALB=$(kubectl get ingress visiontag -n visiontag -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
curl -s http://$ALB/api/classify -F "image=@/path/to/test.jpg" | jq
```

**Success criteria:** JSON containing `predictions`, `latencyMs`, `pod`, and `usage`. Refresh the page a few times and the pod name in the footer changes, which is load balancing you can see.

## Phase 5, Karpenter autoscaling

Karpenter installation is version-specific and involves an IAM role, an SQS interruption queue, and cluster tags. Follow the official Karpenter "Getting Started with EKS" guide for the install itself, then apply the NodePool from this repo.

Prerequisites the install expects:

- Subnets and security groups tagged `karpenter.sh/discovery = <cluster name>` (done in Phase 1a)
- A node IAM role for Karpenter-provisioned instances
- The Karpenter controller installed via Helm into `kube-system`

Then configure the pool:

```bash
sed -i '' "s|<CLUSTER_NAME>|$CLUSTER_NAME|g; s|<KARPENTER_NODE_ROLE>|KarpenterNodeRole-$CLUSTER_NAME|g" \
  k8s/karpenter-nodepool.yaml

kubectl apply -f k8s/karpenter-nodepool.yaml
```

Note the `limits` block in that file. It caps total CPU and memory Karpenter may provision. Without it, a workload requesting more replicas than intended will scale until your bill notices before you do.

Test it:

```bash
# generate load, e.g. with hey
hey -z 3m -c 50 http://$ALB/

# in another terminal
kubectl get nodes -w
kubectl get nodeclaims -w
```

**Success criteria:** new nodes appear while load runs and are removed a few minutes after it stops.

### AWS-managed alternative

Console route: create an **Amazon Managed Service for Prometheus** workspace and an **Amazon Managed Grafana** workspace, then add the Prometheus workspace as a data source inside Grafana. Also enable **CloudWatch Container Insights** from your cluster's Observability tab for out-of-the-box dashboards.

### Application metrics

The backend logs token usage and latency per request:

```
classify pod=visiontag-backend-7c4 latency_ms=142 input_tokens=1580 output_tokens=94
```

To graph these rather than grep them, add a Prometheus client to the backend and expose a `/metrics` endpoint, then add a ServiceMonitor. That is a worthwhile extension and is not yet in this repo.

**Success criteria:** Grafana shows live node and pod metrics, and they move when you generate load.

## Phase 7, security posture

### GuardDuty

Console route: **GuardDuty → Enable**, then **Settings → EKS Protection**. Turn on both:

- **EKS Audit Log Monitoring**, which analyses control plane audit logs
- **EKS Runtime Monitoring**, which deploys an agent to observe container behaviour

Findings appear under **Findings** and can be routed to Security Hub if you enable it.

### Kubescape, optional configuration scanning

```bash
helm repo add kubescape https://kubescape.github.io/helm-charts/
helm repo update
helm install kubescape kubescape/kubescape-operator \
  -n kubescape --create-namespace \
  --set clusterName=$CLUSTER_NAME
```

### Hardening already applied in this repo

- Pods run in private subnets, no public IPs
- The ALB is the only internet-facing component
- Backend pods hold a single IAM permission through IRSA, no static keys
- CPU and memory `requests` and `limits` on every container
- Readiness and liveness probes on both deployments
- Upload size rejected at the API before reaching the model

Worth adding next: NetworkPolicies to restrict pod-to-pod traffic, and a `securityContext` dropping capabilities and running as non-root.

**Success criteria:** EKS Protection shows as enabled, and your first findings appear.

| --- | --- | --- |

## Phase 9, CI/CD with CodePipeline

### 9a. Source

Push this repository to CodeCommit or GitHub:

```bash
git init
git add .
git commit -m "Initial VisionTag platform"
git remote add origin https://github.com/<you>/visiontag.git
git push -u origin main
```

### 9b. CodeBuild projects

Create two projects, one per service, using `buildspec-backend.yml` and `buildspec-frontend.yml`.

Each project needs:

- **Environment:** Amazon Linux, privileged mode enabled (required to run Docker)
- **Environment variables:** `AWS_ACCOUNT_ID`, `AWS_DEFAULT_REGION`, `ECR_REPO_BACKEND` or `ECR_REPO_FRONTEND`, `EKS_CLUSTER_NAME`
- **Service role permissions:** ECR push (`ecr:GetAuthorizationToken`, `ecr:BatchCheckLayerAvailability`, `ecr:PutImage`, `ecr:InitiateLayerUpload`, `ecr:UploadLayerPart`, `ecr:CompleteLayerUpload`) plus `eks:DescribeCluster`

Then register the CodeBuild role with the cluster so its `kubectl` calls are authorised. This step is the one most people miss, and it produces a confusing `error: You must be logged in to the server (Unauthorized)`:

```bash
aws eks create-access-entry \
  --cluster-name $CLUSTER_NAME \
  --principal-arn arn:aws:iam::$ACCOUNT_ID:role/<codebuild-service-role> \
  --region $AWS_REGION

aws eks associate-access-policy \
  --cluster-name $CLUSTER_NAME \
  --principal-arn arn:aws:iam::$ACCOUNT_ID:role/<codebuild-service-role> \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSEditPolicy \
  --access-scope type=namespace,namespaces=visiontag \
  --region $AWS_REGION
```

### 9c. Pipeline

Console route: **CodePipeline → Create pipeline**. Source stage pointing at your repository, then a build stage per CodeBuild project. The buildspecs perform the deploy themselves via `kubectl set image`, so a separate deploy stage is not required.

**Success criteria:** pushing a commit triggers a build, a new image tag lands in ECR, and `kubectl rollout status` reports success.

## API reference

### `GET /healthz`

```json
{ "status": "ok" }
```

Used by the readiness and liveness probes.

### `POST /api/classify`

Multipart form upload, field name `image`.

```bash
curl -X POST http://localhost:8000/api/classify -F "image=@photo.jpg"
```

Response:

```json
{
  "predictions": [
    { "label": "golden retriever", "confidence": 0.94 },
    { "label": "labrador", "confidence": 0.71 }
  ],
  "latencyMs": 142.3,
  "pod": "visiontag-backend-7c4d9f8b6-x2klm",
  "usage": { "input_tokens": 1580, "output_tokens": 94 }
}
```

Error codes:

| Code | Meaning |
| --- | --- |
| 400 | Not an image, or empty file |
| 413 | Larger than `MAX_UPLOAD_BYTES` |
| 502 | Bedrock call failed, or the model returned unparseable output |

## Troubleshooting

**Pods stuck in `ImagePullBackOff`**
Image URI is wrong, or the node role lacks ECR read permission. Check with `kubectl describe pod <name> -n visiontag`. On Apple Silicon, also confirm you built with `--platform linux/amd64`.

**Backend returns 502 on every request**
Usually IRSA or model access. Confirm the annotation resolved:

```bash
kubectl exec -it deploy/visiontag-backend -n visiontag -- env | grep AWS_ROLE_ARN
kubectl logs deploy/visiontag-backend -n visiontag --tail=50
```

An `AccessDeniedException` means the policy or trust relationship is wrong. A `ValidationException` usually means the model ID is not enabled in that region.

**Ingress has no ADDRESS after five minutes**
The Load Balancer Controller is not running or lacks permissions, or your public subnets are missing the `kubernetes.io/role/elb = 1` tag.

```bash
kubectl logs -n kube-system deploy/aws-load-balancer-containers --tail=100
kubectl describe ingress visiontag -n visiontag
```

**`error: You must be logged in to the server (Unauthorized)`**
Your IAM principal is not an EKS access entry. Add it in **EKS → your cluster → Access**, or with `aws eks create-access-entry`.

**Karpenter provisions nothing**
Check the controller logs and confirm subnet and security group discovery tags match your NodePool selectors:

```bash
kubectl logs -n kube-system deploy/karpenter --tail=100
kubectl get nodeclaims
```

**Frontend loads but `/classify` 404s on refresh**
The nginx SPA fallback is not applied. Confirm `nginx.conf` was copied into the image.

## Teardown

Delete in this order. Reversing it leaves orphaned resources that keep billing.

```bash
# 1. Application and add-ons
kubectl delete -f k8s/ingress.yaml          # removes the ALB
kubectl delete -f k8s/
helm uninstall kps -n monitoring
helm uninstall kubecost -n kubecost
helm uninstall karpenter -n kube-system

# 2. Cluster
eksctl delete cluster --name $CLUSTER_NAME --region $AWS_REGION
# or delete the node group then the cluster in the console
```

Then confirm in the console that these are gone, because they bill independently:

- **EC2 → Load Balancers**, no leftover ALB
- **VPC → NAT Gateways**, deleted
- **EC2 → Elastic IPs**, released
- **EC2 → Volumes**, no orphaned EBS volumes
- **VPC**, deleted last, after everything inside it

Check Cost Explorer the next day to confirm charges stopped.

## Notes and caveats

- Placeholders to replace: `<ACCOUNT_ID>`, `<REGION>`, `<OIDC_ID>`, `<CLUSTER_NAME>`, `<KARPENTER_NODE_ROLE>`, `<codebuild-service-role>`.
- The video background and eye logo are placeholders. Swap in your own assets.
- Karpenter's API group and the AWS Load Balancer Controller's install steps change between versions. The manifests here target Karpenter v1.x. Verify against the version you install.
- Bedrock model IDs, request formats, and pricing change over time. Check current AWS documentation if an invocation is rejected.
- Cost figures are estimates for a US region at on-demand rates, not a quote.
